블록 간격 12초를 10초로 줄이는 안이 공식 검토 대상이 됐다

퀵 슬롯(EIP-8198), 블록 간격 12초에서 10초로 · CFI 결정 01:02:49

블록 생성 간격인 슬롯 시간을 12초에서 10초로 줄이는 첫걸음을 헤고타에 넣을지가 이번 스코핑의 최대 쟁점이었고, 양자내성 전환과의 우선순위 충돌이 논쟁의 축이었다.

· Ryan Berckmans: L2와 앱 레이어 팀들이 퀵 슬롯 포함을 강하게 원한다고 전했다. 12초에서 10초로의 단축 자체보다, 슬롯 단축 체계를 지금 시작해 3, 4년 뒤에도 여전히 12초일 위험을 줄이는 것이 중요하다고 했다.

· Barnabé Monnot: 더 나은 UX, 빠른 확정, MEV 누수 감소, 검열 저항 강화 등 가치를 들어 CFI를 요청했다. 스펙은 머지됐고 헤고타 목표는 10초이며, 디커플드 합의 설계 덕분에 10초가 양자내성 전환을 막지 않는다고 확신한다고 했다.

· Matthew Keil (ChainSafe, Lodestar): 저스틴 트라글리아의 우려에 강하게 동의하며 반대편에 섰다. 구현 자체는 쉽지만 짧은 슬롯에 맞춘 클라이언트 CPU 튜닝이 어렵고, 실존 위협인 양자내성(PQ)에 개발 역량을 집중해야 하며, 디커플드 합의가 슬롯 구조를 재편할 것이라 지금의 테스트가 헛수고가 될 수 있다고 했다. 슬롯 조정 기계만 넣고 실제 단축은 미루자는 입장이다.

· Fredrik: 퀵 슬롯의 가치는 인정하지만 양자내성 일정이 앞당겨질 수 있는 상황에서 헤고타를 지연시킬까 우려했다. 기술 구현이 쉽다면 기계만 넣고 12초를 유지한 뒤 나중에 낮추는 중간안도 제시했다.

· Saulius Grigaitis (Grandine): 지지하지 않는다고 밝혔다. 스테이블 컨테이너 때처럼 원하는 팀들이 먼저 구현을 밀어붙여 경험을 공유한 뒤 몇 달 후 다시 판단하자고 제안했고, 바나바스는 보통 CFI 먼저 하고 문제가 보이면 뺀다고 반박했다.

· Łukasz Rozmej (Nethermind, EIP-8037 공동 저자): EL 쪽 블록 처리 꼬리 시간이 50에서 200밀리초라 CPU는 문제가 아니라고 했다. zkVM이 프로토콜 개선을 인질로 잡게 둬서는 안 되며 네더마인드는 CFI에 찬성한다고 밝혔다.

"지금 하지 않으면 슬롯 시간을 줄이기까지 또 3년을 기다려야 하고, 우리에게는 지금 하는 것이 당연한 선택으로 보인다." (Terence Tsao, 00:53:50)

탑업 싱크(EIP-8379), CL이 EL 동기화를 이끌 수 있는가 · DFI 결정 01:26:38

CL이 EL의 동기화 상태를 조회해 싱크를 이끌 수 있게 하는 엔진 API 제안으로, CL과 EL의 역할 분담을 어디까지 정하고 갈지가 쟁점이 됐다.

· Dustin Brody (Nimbus): 홀레스키 펙트라 사고처럼 CL과 EL이 동시에 멈추는 상황에서 복원력을 높이고, 중복 가십 트래픽과 공격 표면을 줄이며, 스토리지 중복 제거를 유연하게 한다고 설명했다. 모두 선택 사항이며 스냅 싱크를 대체하려는 것이 아니라고 했다.

· Łukasz Rozmej (Nethermind, EIP-8037 공동 저자): 네더마인드가 극도로 최적화한 EL 싱크 과정의 통제권을 잃을까 우려했다. 더스틴이 정보 제공용 엔드포인트일 뿐 EL에 아무 행동도 강제하지 않는다고 설명하자, 그렇다면 스펙에 더 명확히 써야 한다고 했다.

· Enrico Del Fante (Consensys, Teku): CL과 EL의 책임 분리에 대한 최종 그림을 정하지 않은 채 양방향으로 선택 기능만 더하는 것은 문제 해결이 아니라고 반박했다. 반대 방향의 EIP가 이미 DFI됐으니 이것도 DFI하고 방향 논의부터 하자고 했다.

· Cayman Nava (ChainSafe, Lodestar): 클라이언트 행동을 강제하지 않으면서 일부가 탐색하고 싶어하는 유연성을 열어주는 작은 엔진 API 수정이라며 지지했다.

· ethDreamer: 엔진 API 수정에 불과하다면 기존 capabilities 엔드포인트를 활용해 하드포크와 분리할 수도 있다고 제안했고, 더스틴은 그 메커니즘이 멀티플렉서 환경에서 신뢰할 수 없다고 반박했다.

"효율적이고 진짜인 중복 제거를 원한다면 결정을 내려야 한다." (Enrico Del Fante, 01:20:29)

선택적 실행 증명(EIP-8025), 포크에 미완성 기능을 실어도 되는가

zkVM 실행 증명(execution proofs)을 의무화 없이 선택 기능으로 스펙에 넣자는 제안으로, 시간 부족으로 결론은 다음 콜로 넘어갔다.

· ignacio: CFI를 제안했다. 특정 zkVM 페어링이나 증명 시스템을 못 박지 않고 선택적 증명의 스펙만 정의하는 것이며, zkVM 작업을 공용 저장소로 합쳐 다른 프로토콜 변경과의 상호작용 분석 위험을 줄이는 것이 핵심 동기라고 했다.

· Łukasz Rozmej (Nethermind, EIP-8037 공동 저자): 실행 증명 자체는 지지하지만 두 가지 문제를 들었다. 역사적으로 포크에 실린 기능은 프로덕션 준비가 끝난 것이었는데 가스 리프라이싱 없이는 안전하지 않은 것을 싣게 되어 커뮤니티에 잘못된 신호를 주고, 위원회가 게스트 프로그램과 zkVM 짝을 고르는 방식은 열린 클라이언트 경쟁 문화를 깬다고 했다.

· ignacio: 그 우려들은 의무 증명에 해당하는 것이지 선택적 증명인 EIP-8025와는 거리가 있다고 반박했다. zkVM 브랜치와 PVD 브랜치를 따로 유지하는 것이 갈수록 비효율적이라며 다음 콜에서 논의를 잇겠다고 했다.

"안전하지 않다는 것을 알면서 사용자가 쓰면 안 되는 것을 싣게 되니, 포크에 넣을 이유를 모르겠다." (Łukasz Rozmej, 01:30:25)
